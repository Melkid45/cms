# Harbstone builder

The admin now uses only the approved library at `frontend/src/components/{sections,layout}`. `scripts/import-sections.mjs` compiles those templates into a typed React node registry with editable field bindings and copies shared images. Pages store variation IDs and content values, never arbitrary HTML. Shared SCSS is imported directly from the frontend; typography stays in its common files. To refresh after changing a source template, run `npm run import:sections`, review field mapping if the structure changed, and refresh the matching screenshots. IDs are unique per section instance.

The page renderer uses the common `section-stack` rhythm (200px at 1920px, 150px at 1440px, 64px minimum). The shared container explicitly resets Tailwind's breakpoint max-width; it is 1820px wide at 1920px and fluid on smaller screens. Header and footer menus have separate placements and editing panels. Older projects that shared a group receive an independent footer copy without losing their existing links; subsequent saves persist the separation. The server rejects cross-placement assignments.

## Local use

Run `npm run dev -- --hostname 127.0.0.1`. Open `/dashboard/pages`. The Northline Studio sample has Home, Studio and Services at `/site/northline-studio/home`, `/studio`, `/services` (the key comes from the website name; see Companies and websites). **Save draft never changes the published page. Publish page updates its public snapshot.** Public routes receive only published snapshots, without draft content or history. Draft slugs and current published URLs are reserved until publication. Layout, menus, brand and form settings are shared site settings and take effect when saved.

Text, images, SEO, section ordering, duplication, layout, multiple menu groups, two-level menus, colors and header/footer logos are connected. Sections can be dragged by their handle, moved with arrow buttons, or hidden without deleting content. Repeated-card variations expose Add, Remove, Duplicate and Move controls (1–30 items per group, or the group's own `max`: hero-v9 Showcase allows 1–5 slides); fixed compositions and linked-tab layouts keep their original structure. Shared fields are grouped into introduction, images and links. Variation changes map content by semantic role, including custom card lists between repeatable variations. Switching a custom list to a fixed composition requires confirmation.

Page history keeps the last 20 previous versions. Restore loads a snapshot into the editor; save or publish deliberately afterwards. Deletion moves a page to Trash and hides its public URL and navigation links. Restore retains the published snapshot and its menu references. A conflicting slug must be resolved before restoring. Change the homepage before moving it to Trash. Keep external backups in addition to this short revision history.

Locally, content and uploaded images are stored in ignored `.data/`, on the server instead of localStorage/IndexedDB. They survive browser and server restarts. Back up that directory with the project. Concurrent edits are protected by revision checks: stale saves return HTTP 409 instead of overwriting newer content. Images are validated/decoded, resized, stripped of metadata and stored as WebP. Plain SVG logos are parsed with a strict element allowlist, reject scripts and external resources, and are rasterized before storage. Original source files and all previous static frontend demo pages are preserved. Old builder renderers/catalog/local browser storage adapters were removed from the admin.

## Vercel / persistent hosting

Configure **DATABASE_URL** for PostgreSQL, **BLOB_READ_WRITE_TOKEN** for Vercel Blob, **CMS_ADMIN_EMAIL**, a unique **CMS_ADMIN_PASSWORD** of at least 12 characters, **CMS_AUTH_SECRET** of at least 32 random characters, and **NEXT_PUBLIC_SITE_URL** for the public domain used in sharing metadata. Use `hosting.env.example` as the checklist and run `npm run check:deploy`. This checks configuration presence; it does not prove external connectivity. Do not commit secrets. The adapter creates its table on first connection. A serverless filesystem is not treated as persistent: hosted writes fail explicitly without storage configuration.

Sign in at `/login` with the configured owner email and password. Dashboard routes and APIs require a signed HttpOnly, SameSite=Strict session with a server-verified 12-hour expiry (Secure in production). Logout clears it. Login attempts are rate-limited in persistent storage. Changing the owner email/password/secret requires server environment access; rotate the authentication secret to revoke all sessions. Open registration redirects to login. Team accounts and automated password recovery are not implemented. Unconfigured local development remains accessible without credentials; production fails closed.

## Enquiries & SMTP

Published contact/footer forms submit to `/api/forms`. Messages are saved in `/dashboard/submissions` before email delivery is attempted. Forms in library/editor previews never send messages. `/dashboard/settings/forms` controls acceptance, recipient and success message, and shows which hosting integrations are configured. Anti-spam uses a hidden field, a signed token valid for 30 minutes (minimum age one second), and a durable per-IP limit of five submissions per ten minutes. Only fields from the actual published form are accepted and validated (required, email syntax, `type=tel` phone characters, `type=number` with its min/max, checkbox and radio values; a radio may be sent as its saved label). A form with `data-calc` (calculator-v40) gets an `estimate` value computed on the server from the width and the saved price per metre. IPs are hashed with the server secret. Expired rate-limit entries are cleaned automatically.

Set **SMTP_HOST**, **SMTP_PORT** (587 by default), **SMTP_SECURE** (`true` for port 465), **SMTP_FROM**, and, when required, **SMTP_USER** / **SMTP_PASSWORD** in the server environment. SMTP credentials are never stored in the project JSON or returned to the browser. Inbox distinguishes saved, emailed and failed delivery; failed mail does not lose the enquiry. Actual mail delivery must be tested with the client's provider before launch. Up to 5,000 messages are retained; at capacity new enquiries fail explicitly instead of silently deleting older data. No external email is sent while SMTP is unconfigured.

## Telegram editing

`/api/builder/bot` is a separate signed endpoint for the trusted local Telegram bridge. GET reads the project, PUT saves it (optional `?publish=<page-id>`), and POST uploads validated media through the same upload service as the UI. Production `CMS_BOT_PUBLIC_KEY` contains only the bridge's base64 SPKI public key. The private key stays outside the repository on the bridge host, and is never passed to the coding process. Signatures bind timestamp, nonce, method, path and body; PostgreSQL stores short-lived single-use nonces. Removing/rotating the public key and redeploying revokes this integration without changing the owner's login.

The bridge gives each coding task a temporary localhost capability and revokes it on completion. CMS edits retain the same schema, revision guards, drafts and history as browser edits. Template edits compile from their frontend sources before checks. `/api/release` exposes only the deployed Git SHA so the bridge verifies the exact Next deployment rather than mistaking a successful push or the legacy static site for publication. See `tools/telegram-bridge/README.md` for setup and the explicit live integration check.

The existing `harbcms.vercel.app` deployment serves the static `frontend` project. The Next builder is a separate application rooted at `admin`; it needs its own Vercel project or a deliberate switch of deployment root. Publishing content in the Next builder is a database operation and needs no Git push/rebuild. Telegram code editing continues to publish the static frontend separately. Do not imply these are the same deployment.

## Companies and websites

The admin manages any number of **companies**, each with any number of **websites**. Every website has its own project document (pages, menus, brand, layout, forms, contacts), media, enquiries/inbox, SMTP settings and backups. The sidebar project card shows the current company and website; clicking it lists the websites you can switch to (inline, no popup). The super admin manages companies on **Clients** (see "Clients section and grouped menu" below): Add company and Add website (blank sample site or a copy of an existing website; internal `/site/...` links of a copy are rewritten to the new address. A copy takes the entered name as its brand name, starts with every page unpublished, and has an empty enquiry recipient and website URL, so nothing goes live or reaches the source website by accident). Website addresses are generated from the name (Cyrillic is transliterated); an address cannot equal a website id, `default`, or a page address of the first website.

The selected website is remembered per browser in the `cms_site` cookie. Every admin API call also sends it explicitly as `?site=<site-id>` (or the `x-cms-site` header); the cookie is only a fallback. An explicit website the account may not open returns 403. `GET /api/builder/sites` returns the visible companies/websites and the current website; `POST` (super admin) with `{action:"company",name}` or `{action:"site",companyId,name,key?,copyFrom?}` creates them.

**Public URLs:** `/site/{site-key}/{page-slug}` (the key is URL-safe and unique, e.g. `northline-studio`). One-segment `/site/{slug}` URLs keep working: `/site/{site-key}` redirects (307) to that website's home page, otherwise a published page of the first website redirects to `/site/{first-key}/{slug}`. Canonical URLs use the website URL setting plus `/site/{site-key}/{slug}`. Enquiry forms send the website id with the token request and submission; tokens are bound to their website.

**Storage keys** (`harbstone_project` table / `.data/`):

| Data | First website (id `default`) | Other websites |
| --- | --- | --- |
| Registry (all companies/websites) | `companies` / `companies.json` | same document |
| Project | `default` / `project.json` | `site:{id}` / `sites/{id}/project.json` |
| Enquiries | `submissions` / `submissions.json` | `submissions:{id}` / `sites/{id}/submissions.json` |
| SMTP | `smtp` / `smtp.json` | `smtp:{id}` / `sites/{id}/smtp.json` |
| Backups | `backup:{uuid}` / `backups/` | `backup:{id}:{uuid}` / `sites/{id}/backups/` |
| Local media | `media/{uuid}.webp` → `/api/builder/media/{uuid}` | `sites/{id}/media/{uuid}.webp` → `/api/builder/media/{id}/{uuid}` |
| Blob media (new uploads) | `cms-media/default/{uuid}.webp` | `cms-media/{id}/{uuid}.webp` |

Accounts and sign-in/password rate limits stay global. Old Blob URLs (`cms-media/{uuid}.webp`) and old local media URLs keep resolving.

**Migration** is automatic and idempotent: when the registry document is missing, it is created with company 1 / website 1, both with id `default`, named after the existing brand. The first website keeps the pre-multi-site keys and files, so no data is copied or moved. Revision checks and `FOR UPDATE` locking work per website document; creating a website inserts its project document in the same transaction as the registry update.

The signed bot endpoint accepts `?site=<site-id or key>`; without it, it uses the first website. Other websites are available only to the `super-admin` actor; the `client` actor stays on the first website (403 otherwise). `?resource=sites` lists the websites the actor may use. The bridge CLI takes `--site=<site-key>` and has a `sites` command.

## Website orders, billing and change requests (2026-11-18, skeleton)

**AI summary (paid, optional).** When a client submits the interview, `writeAiBrief` (`lib/builder/orders.ts`) runs after the response (`after()`). It asks OpenRouter (`lib/builder/ai.ts`) for a team summary, site map, content list and risks, and stores it as `order.aiBrief`, shown on the order page. It is off unless `CMS_AI=1` and `OPENROUTER_API_KEY` are set. Every call has a token cap. The spend per month is stored in the `ai-usage` document from the exact cost reported by OpenRouter, and calls stop at `CMS_AI_MONTHLY_USD` (default 10). Default model: `google/gemini-2.5-flash-lite` (about $0.0001–0.0003 per order).

- **Public order flow:** `/order` is a chat-style interview (script in `src/lib/builder/interview.ts`, first step: upload an existing brief). Answers save as they go (`/api/orders/[id]`, client key in `x-order-token`, only its hash is stored). Submit builds a plain-text brief (`buildBrief`); the client confirms it and picks a package (Standard / Designer pack) and hosting (monthly / yearly) → `/api/orders/[id]/confirm` creates a company + draft website from the sample site and starts billing. Status page: `/order/[id]#t=<token>`. Brief files are private (`.data/orders/<id>/` or `order-file:<id>` rows).
- **Team:** `/dashboard/orders` (owner + designers): orders with "needs action", brief, files, designer assignment (gives the designer access to the website), tasks, notes, client login creation (password shown once). Tab "Change requests": clients ask for non-content changes from their Overview, the owner quotes a price, the client accepts → invoice + notification.
- **Billing** (`/dashboard/billing`, owner, `src/lib/builder/billing.ts`): setup fee per package, monthly/yearly hosting, paid modules (custom blocks offered as add-ons), invoices (marked paid by hand — no card payments connected), renewal invoices, reminders (team notification + client email when SMTP of the first website is set), suspension after `graceDays` (public pages show "temporarily unavailable"). Daily `/api/cron/billing` (Bearer `CRON_SECRET`); it also runs when the owner opens Billing.
- **Notifications:** `src/lib/builder/notifications.ts`, bell in the admin shell (owner + designers), email to `CMS_ADMIN_EMAIL` when SMTP is configured.
- **Website style:** `project.customCss` (Settings → Website style, design roles only), validated on save (no tags/@import/external URLs), rendered inside `.site-canvas`.
- **Section background:** `section.tone` = tint | dark | accent (editor: Background select, design roles only). Rendered as `data-tone` on the section; colours are swapped in `site.scss` from `--brand-*` (the site palette after custom CSS) and `--brand-on-accent` (black/white by contrast, from `site-canvas.tsx`).
- **Library refresh:** `frontend/src/styles/template/_refresh.scss` loads after all section styles: no hairline dividers, no eyebrow labels, larger nav/buttons/small text, FAQ items as cards.
- **Website fonts:** `project.fonts` = a font pair id from `src/lib/builder/font-pairs.ts` (free Google pairs with Latvian + Cyrillic, default Playfair + Inter; also "Inter" only and "DM Serif Text + Plus Jakarta Sans", whose headings have no Cyrillic), picked on the same screen, design roles only. Fonts are self-hosted by next/font in `src/components/builder/site-fonts.ts` with `preload: false`, so a page downloads only its own pair. Headings use `--font-heading` / `--font-heading-weight`, text `--font-body`.
- **AI:** not connected. Interview, brief analysis, draft building and quotes are scripted/manual; AI needs an owner decision (model, key, cost cap).
- Storage: installation documents `orders`, `notifications`, `billing`, `change-requests` (Postgres rows or `.data/*.json`) via `src/lib/builder/doc-store.ts`.

## Multilingual websites (2026-11-19)

- **Setting:** `project.languages = { default, enabled[] }` (lv / ru / en / de), Site layout → Languages (design roles). Absent or one language = single-language website, everything works as before.
- **URLs:** pages of the default language keep `/site/{key}/{slug}`; pages of other languages live at `/site/{key}/{locale}/{slug}` (route `app/site/[site]/[slug]/[page]`, shared logic in `app/site/[site]/public-page.tsx`). A page opened under the wrong prefix redirects to its real address; `/site/{key}/{locale}` opens that language's home page (the home page or its translation). Slugs stay unique per website and cannot be a language code. Helper: `pageHref()` in `lib/builder/i18n.ts` — use it instead of `sitePath()` for page links.
- **Data model:** `page.locale` + optional `page.translationGroup` (pages sharing a group are translations of each other; the server allows one active page per language in a group). Menus get an optional `locale` (a menu is shown only on pages of that language; empty = all). Header/footer texts per language: `layout.localized[locale].header|footer` = value overrides merged over the default values (Site layout → Edit header/footer content → "Texts for language"; only differing values are stored).
- **Editor:** page editor → "Language & translations": page language, and for every other enabled language either the linked translation (open it) or "Choose a page" + link / "Create XX copy" (clones the sections into a new draft page with slug `{slug}-{locale}` and opens it), plus "Unlink this page". Saves immediately; the draft must be saved first.
- **Public page:** `<html>`-level `lang` on `.site-canvas`, `<link rel="alternate" hreflang>` for every published translation plus `x-default` (default language), canonical from the website URL. Form status texts (Sending…, errors) follow the page language (`uiText()`).
- **Language switcher:** any header template element with `data-lang-switcher` (all headers have an empty `div.site-header__langs` in their actions) is filled with LV / RU / … links to the current page's translations (or that language's home); nothing is rendered on single-language websites. Styles `.lang-switcher*` in `components/builder/site.scss`; a site can restyle it (enrina: dropdown pill in its custom CSS).
- **Menus as columns:** `nav[data-menu-expanded]` in a header/footer template renders each top-level menu item as a column (parent link + its sub-pages) instead of a dropdown (header-v30 Mega uses it).
- **Formatted text:** a template element with `data-rich-text` renders its field as blocks: blank line = paragraph, `- ` lines = bulleted list, `1. ` = numbered, `### ` = sub-heading, `**bold**`, `[label](url)` (safe React elements, never HTML; `components/builder/rich-text.tsx`).
- **Permissions:** same as page create/edit: translations, `languages`, menu locales and layout texts are structural (super admin / designer); clients get 403 from `clientProjectError` (`languages` compared there, the rest via pages/menus/layout).
- **Not yet:** translated slugs of the default language under a prefix, per-language SEO for the website name, translating section texts automatically. (sitemap.xml: see SEO.)

### Instant checkout popup, no cart (Zcena, 2026-11-22)

- **Setting:** Website settings → **Shop cart** → "Instant checkout popup (no cart)" = `project.store.checkout = "popup"` (`cart` is then removed; `store.cart` became optional). Zcena is set to it. Other websites keep the cart / checkout page.
- **Behaviour** (`components/builder/checkout-popup.ts`, opened from `cart-widgets.ts`): no header cart link; order buttons of cards (pricing-v20/v21), the product page (pricing-v22, chosen options + picked case) and the configurator (pricing-v23) get `href="#order"` at runtime and open a popup for that one product — a 1:1 rebuild of the prototype's `checkout(p, c)`: left picture / title / short configuration / price lines (product, pickup or delivery · zone, ready in 2–4 working days, total + the display currency "≈ $…") / hint; right private/company tabs, registration number lookup, name, phone + e-mail, pickup/delivery tabs, pickup point (address, hours, note, Google Maps, Waze — read from the delivery block contact-v20), delivery address with suggestions + "My location" + flat/note, customer account (signed in → "saved to your account"; guest → "create an account" + password, registers through `/api/shop/account`), status messages WhatsApp/Telegram, newsletter, submit, terms (links the site's warranty/terms page found on the page). After sending: "thank you" with the order number, lines, "Open the order" (signed-in buyers → account page `#order-N`), Done. ## Analytics (2026-11-19)

First-party website statistics inside the CMS: nothing to install or connect, no cookies, no third parties, so no consent banner.

- **Collection:** `components/builder/site-analytics.tsx` is rendered only by the public page route (`app/site/[site]/public-page.tsx`), never in the editor, previews or the library; it also stays silent inside iframes, for `navigator.webdriver` (automation, screenshot scripts) and for browser-prerendered pages until they are really opened. It sends `navigator.sendBeacon` to `POST /api/builder/track`: a `view` (referrer, `utm_source/medium/campaign`), a `leave` with the time the page was visible (on `visibilitychange`→hidden / `pagehide`), and an `action` for clicks on `tel:`, `mailto:`, WhatsApp (`wa.me`, `api.whatsapp.com`), Telegram (`t.me`) links and links that open a pop-up with the price calculator (`form[data-calc]`).
- **Server is the authority** (`app/api/builder/track/route.ts`): zod-validated 2 KB body, same-origin only, the website must exist, not be suspended and the page must be published (cached 30 s per instance); bot user agents, prefetch/prerender requests and requests with a valid CMS session cookie (owner, team, clients) are ignored; 60 calls per minute per address (per server instance). The response is always 204 (400/429 for malformed/limited). Device class comes from the user agent, browser language from `Accept-Language`, country only from a proxy header (`x-vercel-ip-country` on Vercel, `cf-ipcountry` when a `cf-ray` is present), otherwise "Unknown".
- **Privacy:** a visitor = first 12 chars of SHA-256(daily random salt | website | IP | user agent). Salts live in the `analytics-salt` document only for yesterday/today/tomorrow (UTC) and are then deleted; the per-day hash lists are deleted as soon as the day is over. Nothing personal is stored; visitors cannot be followed across days. "Visitors" over a period = sum of daily unique visitors.
- **Storage** (`lib/builder/analytics.ts`, via `doc-store.ts`): one document per website and month `analytics:{site}:{yyyy-mm}` (Postgres row or `.data/analytics-{site}-{yyyy-mm}.json`) with daily counters: views, visits (views not referred by the site itself), visitors, visible time, contact actions, and per page views/visitors/time/actions, plus sources, UTM, devices, countries, languages (max 300 keys per dimension and day, the rest is "Other"). Hits are buffered in memory and written together after 1.5 s (`after()` keeps serverless instances alive for the write). Days use the website time zone (Settings → enquiry time zone). Retention: month documents older than 400 days are deleted.
- **Enquiries and conversion:** read from the website inbox at report time (`createdAt`, `pageId`); enquiries flagged Spam or Test are not counted. Enquiry conversion = enquiries ÷ visitors, per website and per page.
- **Shop orders:** read from `shop-orders:{site}` at report time; cancelled orders are not counted. Tiles Orders, Revenue (order totals per currency) and Order conversion (orders ÷ visitors), an Orders chart and Orders / Revenue / Order conv. columns appear only on websites that have ever received an order. Per page, an order counts for every page whose products it contains (the page the "Order" button was on), with the revenue of those products. Orders are **not** linked to UTM campaigns: the landing URL with UTM is not carried to the checkout without storing something in the visitor's browser, which analytics deliberately avoids (possible later: let the cart, which already uses localStorage, remember the landing UTM and send it with the order).
- **Dashboard:** `/dashboard/analytics` (menu "Analytics", all roles; clients and designers only for websites in their scope — `GET /api/builder/analytics?site=&days=7|30|90` uses `authorizeSite`). Website picker (switches the current website), period 7/30/90 days compared with the previous period, KPI tiles, chart by day (visitors / page views / enquiries / contact actions, plain SVG), pages table with conversion and average time, sources, contact actions, campaigns, devices, countries, languages. **Reset analytics for this website** (super admin, `DELETE /api/builder/analytics?site=`) deletes the website's analytics documents; enquiries stay.
- **Testing:** `../../.run/analytics/selftest-traffic.mjs` opens the pages of the test website `test-studio-qa` in headless Chrome as several visitors (marked `utm_campaign=analytics-selftest`, one bot that must be ignored); `shot-dashboard.mjs` screenshots the dashboard. Reset the test website's analytics afterwards. `shop-test.mjs` adds marked views and one test order ("Analytics TEST") on zcena; `--cleanup` deletes the order and resets zcena analytics.
- **Not yet:** orders/revenue per UTM campaign (see above); no per-visit paths or sessions; time on page is reported only by browsers that deliver the `leave` beacon.

### Analytics v2: live, funnels, goals, clicks, scroll, weekly report, CSV (2026-11-19)

Same privacy model (no cookies, no browser storage, daily-salt visitor hash, nothing typed is ever sent).
- **Beacon additions** (`site-analytics.tsx` → `POST /api/builder/track`, new `t` values): `event` (`e` = funnel step), `click` (`k` = `section id|nth-child path inside the section|link/button text`, max 40 per view; only `a[href]`, buttons, `[role=button]`, `summary`, submit inputs — never clicks into fields), `scroll` (`d` = deepest of 25/50/75/100 %, once per mark), `ping` (after 15 s, 30 s, then every 60 s while visible, max 30; Live now + time fallback). The server hashes the visitor for events, actions and pings too.
- **Time on page (fixed 2026-11-19):** visible time is reported in parts — each ping carries `ms` since the last report, the `leave` beacon (on `visibilitychange`→hidden and `pagehide`) the rest; `f: 1` marks the first part of a view, which alone increments `timed` / page `n` (a leave without `f` from older cached pages counts as first). So a lost final beacon costs at most the time since the last ping. Why tests showed "—": headless Chrome sends beacons from an unloading page from the browser process **without** the CDP user-agent override, i.e. as `HeadlessChrome`, and the bot filter dropped them. Real browsers were not affected by that, but the ping fallback is new. Test scripts must pass the user agent as a Chrome launch flag (`--user-agent=`): `../../.run/analytics/v2/time-test.mjs` (same-tab navigation, hidden tab, killed browser → time from pings only).
- **Funnel steps** (`funnelSteps` in `lib/builder/analytics.ts`), counted once per visitor and day (`steps` + day-only `seenSteps` hashes, deleted when the day is over): `product` (a page with `.pricing__shop-card`, `[data-product]` or `[data-configurator]` was viewed), `cart` and `order` (dispatched by `cart-widgets.ts`: `window.dispatchEvent(new CustomEvent("cms:track", { detail: { e } }))` — any widget may send a step this way), `checkout` (page with `.pricing--checkout`), `form_start` (first focus in a `form[data-cms-form]`), `form_sent` (the form's `cms:sent`, caught in the capture phase). Checkout, search (`#search`), account (`#account`) and password forms are not lead forms. Contact actions also count unique visitors per kind (`a:phone`, …, `a:any`).
- **Storage:** optional per-day fields `steps`, `clicks[page]` (max 300 keys per page and day), `scroll[page]` = views that reached 25/50/75/100 %. Older days simply lack them.
- **Live now:** visitors whose last hit (view, action, event, ping) was within 5 minutes, per page. In memory per instance and mirrored on each flush to `analytics-live:{site}` (keys = hash of the daily visitor hash). `GET /api/builder/analytics?view=live`; the tile refreshes every 15 s.
- **Goals:** `analytics-config:{site}` (`lib/builder/analytics-config.ts`, max 20). Types: page visited (unique visitors of the page), contact action (unique visitors with that action, or any), form sent (inbox enquiries, whole website or one page), order (shop orders, whole website or orders with products of one page). Computed from stored statistics at report time, so a new goal shows past periods too. Conversion = completions ÷ visitors, compared with the previous period. `POST /api/builder/analytics` adds, `DELETE ?goal=id` removes (every account with access to the website).
- **Click map + scroll depth:** `GET ?view=clicks&page=&days=` → ranked elements and scroll marks. The dashboard shows the ranked list and the published page in a same-origin iframe (1280 px wide, scaled; 390 px on phones) with numbered dots placed on each element by its path (links inside the preview do nothing; the beacon is silent in iframes). Elements not found or hidden now (e.g. inside the closed mobile menu) are marked "not on the page now". Paths use `nth-child`, so heavy edits of a section move or drop old dots.
- **Weekly report:** `buildWeeklyReport(siteId)` / `sendWeeklyReport(siteId)` in `lib/builder/analytics-weekly.ts`: last 7 days vs the 7 before (visitors, views, enquiries, enquiry conversion, contact actions, orders and revenue for shops, top 5 pages, goals) as plain text. Delivery is **opt-in per website** (Analytics → Weekly report, super admin switches, `PATCH /api/builder/analytics {email, telegram}`): e-mail to the form recipient through the website's SMTP (`mailConnection`), Telegram through the website's CRM bot (`crm/telegram.ts`, sent only when connected). Other channels: `registerWeeklyReportChannel()`. Cron `GET /api/cron/analytics-report` (Bearer `CRON_SECRET`, like backups; in `vercel.json` Mondays 06:00 UTC) sends for websites with a switch on, at most once in 6 days; no switch / no channel → nothing. The dashboard shows a preview (`?view=weekly`) and whether each channel is ready.
- **CSV export:** "Export CSV" on the pages table (views, visitors, enquiries, conversion, orders, revenue, actions, avg. time, scroll %) and "CSV" on the chart (daily series), built in the browser (UTF-8 BOM, formula-like cells prefixed with `'`).
- **Reset** also clears the live document; goals and weekly settings are kept.
- **Testing:** `../../.run/analytics/v2/selftest-v2.mjs` (test website test-studio-qa, `utm_campaign=analytics-selftest`, 4 visitors: real link clicks, scrolling, form focus on /services, a `cms:sent` event without a real enquiry, synthetic shop funnel events; `--goals` adds TEST goals, `--check` prints live/funnel/goals/clicks/weekly from the API, `--cleanup` deletes TEST goals and resets the website's analytics). Note the 60 beacons/min/IP limit: all local visitors share 127.0.0.1. `shot-v2.mjs` → `analytics-v2-1440.png`, `analytics-v2-390.png`.

Unaudited apps can only post privately (`SELF_ONLY`).
  - The networks pull images from `/api/social/image/{siteId}/{mediaId}.jpg` (public; a JPEG copy of a `social-*` render only, anything else is 404).
  - **Publish now** is disabled and the server answers 409 "not connected — ask the administrator" until that network is connected.

OAuth: `/api/builder/social/oauth/{meta|tiktok}` → consent screen → `/api/builder/social/oauth/{meta|tiktok}/callback` (single-use state stored on the server plus a Lax cookie, because the session cookie is SameSite=Strict and is not sent on the network's redirect). ## CRM: contacts, deals, tasks, notifications (2026-11-19)

A small-business CRM per website, in the admin menu as **CRM** (badge = overdue tasks) with tabs Contacts / Deals / Tasks / CRM settings. Code: `src/lib/builder/crm/` (`shared.ts` types for both sides, `store.ts` storage + ingestion, `actions.ts` zod schemas, mutations, overview, `events.ts` hooks, `telegram.ts`, `access.ts`), UI `src/components/admin/crm/`, API `/api/builder/crm*`.

- **Storage:** one locked document per website `crm:{siteId}` (Postgres row / `.data/crm-{siteId}.json`) via `doc-store.ts`: contacts, deals, tasks, stages, settings, plus `synced` ids of enquiries/orders already turned into contacts (deleting a contact therefore sticks). Enquiries and shop orders stay in their own stores; a contact keeps only their ids, and enquiry count, orders, revenue (cancelled orders excluded), last activity and the timeline are computed when read. Limits: 5,000 contacts / deals / tasks, 300 timeline events per contact.
- **Contacts from enquiries and orders:** `after()` hooks in `/api/forms` (`onEnquiry`) and `/api/shop/orders` (`onShopOrder`) create or update the contact right after the response; `syncSources()` also runs on every CRM read, so enquiries/orders from before the CRM (or from a failed hook) are picked up. Form fields read: `name` / `first_name`+`last_name`, `email` (or any value that looks like one), `phone`/`tel`, `contact`, `company`, `utm_source/medium/campaign` when a form sends them. Crawlers read robots.txt only at a host root, so the shared CMS host also has `app/robots.ts`: admin paths disallowed, hidden/suspended websites disallowed, every website's sitemap listed, training-only bots blocked per website.

Only when the Website URL is a real https domain and the server runs in production; never from local/tunnel. Answered with Next's `permanentRedirect` = **308** (permanent; Google treats 308 like 301 — a literal 301 would need a proxy/route handler in front of the page routes). Paths are stored normalised (lower case, no query, no trailing slash).

- **Audit** (`seo/audit.ts`; the published version, or the draft of an unpublished page): title length, description, duplicate titles/descriptions across the website, exactly one non-empty H1, heading order (no skipped level), image alt texts, broken internal `/site/{key}/…` links (redirect sources count as valid), image weight (media library sizes; >500 KB per image, >3 MB per page), text length, missing published translations, noindex, social image. ## AI SEO assistant (SEO pack, 2026-11-19)

The client's idea "the system keeps adjusting texts for SEO", done safely: the assistant **only proposes**; a person approves every change (Google's scaled-content-abuse policy: improving existing pages is fine, mass-producing pages is not). Code: `lib/builder/seo/assistant.ts` (server), `assistant-shared.ts` (types, labels), `assistant-prompts.ts` (prompts), `fields.ts` (field address of every heading / text / alt / link of a page). Screen: **Dashboard → SEO → AI SEO assistant** (`/dashboard/seo/assistant`, `components/admin/seo-assistant.tsx`; clients get a "SEO assistant" menu item). Store: document `seo-assistant:{siteId}` (settings, suggestions, runs, content-hash cache, monthly cost, score snapshots, report log).

- **Gate:** the SEO pack (`seoPack`). Without it the API answers 402 (run / read for clients) or 403 (client approvals).
- **Run** (on demand, or monthly): published, indexable pages, worst audit score first, up to *Pages per run*. Free rules: outdated copyright years (fix) and recent years in texts (advice), internal links ("See also" with 1–2 related pages of the same language, appended to a formatted text field), missing translations (advice), numbers that differ between the LV/RU/EN versions of a page (advice), texts left in the other language (sent to the AI for translation). AI tasks chosen from the audit: SEO title / description (length rules, duplicates), missing alt texts (from the text around the image + file name; the AI does not see the picture and the reason says so), 2–4 FAQ entries from the page's own text when it has fewer than 3 (into the existing FAQ list, or a new FAQ section in the variant the website already uses: structural, design roles only), question-style H2 (not in contact/CTA/FAQ blocks), clearer H1 when shorter than 10 characters, a short direct answer prepended to the first formatted text when its first paragraph is long, a list or off-topic. Search Console queries: hook = `PageTask.faq` (add real queries there once the API is connected).
- **No invented facts:** the prompt forbids prices, numbers, guarantees, addresses, years, ratings etc. that are not on the page; after the answer every new text is checked against everything the website says (published pages, SEO texts, business details): unknown numbers, promise words (garantija / гарантия / guarantee / free / best…) and language problems (Latvian without diacritics, Cyrillic in LV/EN, non-Russian RU) become **flags** and raise the risk.
- **Prompts per language** (`assistant-prompts.ts`): LV (diacritics ā č ē ģ ī ķ ļ ņ š ū ž always, Jūs, case agreement, no calques), RU («вы», no канцелярит, «ёлочки»), EN (plain British, no hype words), DE (Sie, umlauts). Bumping `PROMPT_VERSION` makes cached pages be re-checked.
- **Cost:** model = `CMS_AI_MODEL` via `aiComplete` (OpenRouter, `CMS_AI` flag, installation cap `CMS_AI_MONTHLY_USD`); per-website **monthly budget** (default $0.50; the run stops when it is reached), pages of one language batched 3 per call, `response_format: json_object`, content-hash cache per page (an unchanged page is not sent again). Every run logs pages, calls, tokens, cost and cost per page; month-to-date cost is on the screen. Measured on enrina (gemini-2.5-flash-lite, 3 pages LV+RU, 2026-11-19): $0.0016 in 3 calls (one wasted by an answer-format bug, fixed), ≈ $0.0002–0.0007 per page.
- **Mock / test mode:** `CMS_AI_MOCK=1` (whole installation, any `aiComplete` caller) or `aiComplete({ mock, useMock: true })` returns canned text: no network, no cost, not counted. The assistant's per-website **Test mode** (settings) and `{"action":"run","mock":true}` (super admin) use it; such suggestions carry the flag "Test mode: canned text".
- **Queue:** each suggestion = type, page, language, reason, impact, risk, flags, and changes with before/after (word diff). **Approve** applies to the draft; with "Publish right after approving" the same change is also written into the published copy only (other unpublished draft edits stay unpublished; a "Published" history entry is added; IndexNow / OG image via `afterPublish`). **Edit** (then approve), **Revise** (AI rewrite by an instruction), **Reject**. **Approve all low-risk** = meta texts and alt texts without warnings. Advice items (no automatic change) are "Mark as done". A change is applied only while the field still has the "before" value (else 409; older pending items become "Out of date" on the next run). **History** lists decided items; **Undo** restores the previous value (draft, and the published copy when it was published) or removes the added FAQ cards / section.
- **API for other modules (approvals bot):** `GET /api/builder/seo/assistant?site=` → `{ suggestions[] (status pending | approved | rejected | undone | stale), settings, runs, month }`; `POST {action:"approve"|"reject"|"undo", ids[], publish?, edits?: {id: {changeIndex: text}}}`; `POST {action:"revise", id, change?, instruction}` → the rewritten suggestion; `POST {action:"run", maxPages?, pageIds?}`; `POST {action:"settings", …}` and `{action:"send-report", month?}` (super admin); `GET ?view=report&month=yyyy-mm`. Server functions: `runAssistant`, `decide`, `revise`, `buildReport`, `sendReport`, `monthlyTick` in `seo/assistant.ts`.
- **Monthly:** `GET /api/cron/seo-assistant` (Bearer `CRON_SECRET`; in `vercel.json` on the 1st at 05:00 UTC): only websites with the pack and *Monthly run* on, once per month; runs the assistant and sends last month's **report** (approved changes, audit score at the month's first run → now, views/visitors of changed pages in the last 30 days vs the 30 before from the analytics module, next recommendations, AI cost) through the Analytics → Weekly report channels (e-mail / Telegram) that are switched on. The report is also on the screen (month picker, "Send now" for the super admin).
- **Permissions** (ACCESS.md): read the queue — every account with access to the website (clients only with the pack); run — super admin and designers; approve / reject / undo / revise — super admin, designers, and clients of that website when it has the SEO pack (not structural items; page/section client locks are respected); settings and sending the report — super admin.
- **Tests (outside the repo):** `../../.run/ai-seo/test-mock.mjs run|decide` (test-studio-qa: pack + test mode on, run, cached re-run, approve to draft / edited + publish, revise, new FAQ section, reject, undo), `real-enrina.mjs` (the one paid run, suggestions left pending), `client-check.mjs`, `shot-assistant.mjs` → `.run/ai-seo/shots/`.
- **Not yet:** Search Console / Bing queries (hook only), header/footer (layout) texts, a vision model for alt texts, translated slugs, recurring invoice for the pack.

## Booking (online appointments, 2026-11-19)

All texts are fields of the block (hidden label list), so each page language has its own; dates use the page locale (`Intl`). Mobile first, buttons with `aria-pressed`, labelled groups, live status, focus kept across re-renders. In the editor/library (no published page) it shows sample data or the real services and never books.
- **API:** `GET /api/booking?site=` (services, staff, today/last day), `&service=&staff=&month=yyyy-mm` (open days), `&service=&staff=&date=` (free times). `POST /api/booking` — zod, signed page token (`/api/forms/token`, page must be published with a visible contact-v60), honeypot `website`, 5 bookings per visitor per 10 minutes (`limitBookings`), forms switched off → 404; errors in the page language (`formMessage`).
- **Customer link:** `/booking/cancel?site=&id=&t=` — `t` = HMAC of site + booking id (key from `CMS_AUTH_SECRET`); shows the booking (texts LV / RU / EN / DE by the booking's locale), `.ics` download (`/api/booking/manage?…&format=ics`) and **Cancel** while it is Pending/Confirmed and in the future. Wrong token = 404.
- **E-mail:** when the customer gave an e-mail and the website SMTP is configured, `confirmToCustomer` sends a confirmation in the page language with the .ics attached and the cancel link (link host = `NEXT_PUBLIC_SITE_URL`, else the request host); otherwise nothing is sent (`email: none`).
- **CRM:** every booking creates or updates a contact (e-mail, then phone; source "Online booking"), stores `contact.bookingIds` and adds a timeline event (`kind: "booking"`); team changes (status, move) add events too (`onBooking` in `crm/events.ts`, after the response). - **Analytics:** a successful booking dispatches `cms:track {e:"booking"}` (funnel step `booking`, panel "Online booking"); new goal type **Booked online** counts website bookings (not cancelled, not TEST) per day, whole website or one page.
- **Dashboard → Bookings** (menu for super admin and clients; designers 403 like the CRM — `crmRoute` + `crmAccess`): Calendar (day = a column per staff member, week = a column per day, staff filter, working hours shaded, now line, overlapping bookings side by side; click an empty time → new booking; click a booking → status Pending / Confirmed / Cancelled / No-show / Done, move to another time with the free times listed, "allow outside the hours or over another booking", internal note, history), List (upcoming / by status, search), Services & hours. ## Onboarding autopilot (2026-11-19)

"Full pack": the customer describes the business once; the system interviews, writes the brief, builds a draft website from the library, lets the customer comment on any block (text or voice), translates and publishes. Code: `src/lib/builder/onboarding/` (`shared.ts` client-safe types, questions, niche plans; `store.ts` storage, access, AI wrapper; `consult.ts` interview, old-site import, brief; `content.ts` generic section ⇄ AI bridge; `generate.ts` draft website; `review.ts` comments/approvals + API for other channels; `translate.ts` translation + publish; `fetch-site.ts` old-website reader; `actions.ts` zod actions), UI `src/components/onboarding/`.

- **Steps** (`record.step`): Consultation → Draft → Your review → Translation → Live, shown as a tracker to the customer and in the admin list.
- **Start:** (1) automatically when a client confirms a website order (`/api/orders/[id]/confirm` → `startForOrder`; the order interview's business/offer answers are offered as suggestions); the order status page `/order/[id]` then shows "Open the consultation" (`GET /api/onboarding/by-order/[orderId]`, order token). (2) Dashboard → **Onboarding** → "Start an onboarding" (super admin): new company + website (sample site) + a private client link `/onboarding/{id}#t=<token>` shown once ("New client link" rotates it). The "Test" box makes a **test record**: `mock` + `test` (simulated AI, no cost, never published by the customer, website hidden from search engines).
- **Access** (`authorizeOnboarding`): header `x-onboarding-token` = the record's private token (sha256 stored) or the linked order's token → customer; otherwise the CMS session: super admin, designers and client accounts of that website (`canAccessSite`). Team-only actions: new link. `/dashboard/onboarding*` is open to all roles (`clientRoute`), the list shows only websites in scope.
- **Storage:** one locked document `onboarding` (`.data/onboarding.json` / Postgres row): chat, answers, suggestions, brief, plan, pages, review items (history with the previous section texts for undo), translations, AI log, events.
- **Consultation:** scripted adaptive questions (`TOPICS` in `shared.ts`): business, old website/social link, niche (guessed from keywords EN/LV/RU, confirmed by the customer), offer (wording per niche, e.g. menu with prices for cafés), audience, differentiators, competitors, tone, colours, photos (upload into the website's media library through `storeMedia`, max 30), contacts, opening hours (wording per niche), languages (first = main), goal (options per niche), pages. After the script AI writes up to 3 follow-up questions for gaps (once), in the consultation language. Answers by text or **voice**.
- **Consultation language** (`record.lang`: lv / ru / en, `onboarding/i18n.ts`, translated by hand, no AI): questions, hints, option labels (stored values stay English, so the brief logic does not change), the assistant's messages, the tracker, the answer box and the brief editor. Default: the first website language the client chose in the order (LV/RU/EN), otherwise the browser language (set on first open); the client can switch (LV / RU / EN pills above the chat, action `lang`). The review screen is still English.
- **Old website:** `importSite` reads up to 4 public pages of the same host (start page + about/menu/services/contact links): visible text, title/description, image URLs. Hardening: http(s) on 80/443 only, every hop resolved to public IPv4 and the socket pinned to the checked address (no DNS rebinding), 1.5 MB / 10 s per page, max 3 redirects, HTML only. AI extracts facts (only from the text) → offered as answers ("From your website: … Use this").
- **Brief:** AI (JSON) from the answers, validated by `briefSchema`; facts are never invented — missing facts go to `unknowns`; pages and languages the customer chose are kept. The customer edits every field (offers as `name | price | description | category` lines) and confirms.
- **Draft website** (`buildDraft`): niche plan (`NICHES` in `shared.ts`, home pages copied from the designer-made demo websites: cafe, restaurant, beauty/barber, dental, auto, construction, shop, studio, other services; inner pages About / Services / Prices (Menu) / Gallery / Reviews / FAQ / Contacts; booking niches get contact-v50) → style preset + its font pair (`style-presets.ts`), header/footer variant, brand colours (accent from the client's hex colour if given). One AI call per page writes every text field and list of every section (`content.ts`: field keys, roles and current example texts; lists mapped onto card templates by position; images, links and videos are never written by AI); the home call also writes the header/footer. Unknown single facts become `[placeholders]` (listed on the review screen as "To fill in"). **Lists are never filled with filler:** a list without real items in the brief is emptied (the server keeps at least one card per list, so it becomes one card without texts); a list the answer leaves out is emptied too, and texts missing in a row are empty, never the template's English samples. In blocks with several lists (menu categories of pricing-v50) the emptied list's own title/note are cleared (`groupOwnFields` finds them in the template tree), so the template hides that group; a block whose lists are all empty (no team, no reviews, no gallery) is hidden and gets no review item. Client photos fill image fields in page order (team/testimonial portraits excluded); without photos café/restaurant use the bakery library photos, others keep the template pictures. Pages are saved as **drafts**, `project.languages = {default: main, enabled: [main]}`, `seo.hideSite = true` until publishing; the website's sample pages are replaced (pages published after the onboarding started are never overwritten).
- **Review:** the customer sees each page in the real renderer (`/canvas` via `SiteFrame`, desktop/phone width), clicks a block → comment by text or voice → AI rewrites only that block (`requestChange`; previous texts kept, "Undo last rewrite") → new version shown; "Approve this block" / "Approve all". When every main-language block is approved the step becomes Translation. Deep link `?item=<review item id>`.
- **Translation:** the customer picks languages; one AI call per page and language (header/footer texts with the home page → `layout.localized`); new draft pages `{slug}-{locale}` in the original's `translationGroup`, language-filtered menu copies, `languages.enabled` extended; translated blocks get their own review items. The business name is never translated; the home page is titled Sākums / Главная / Home / Startseite.
- **Publish:** when every block in every language is approved: all pages are published (`writeProject` per page), `hideSite` switched off (stays on for test records); customers cannot publish a test record.
- **Approval items for other channels** (Telegram approvals bot): `listApprovalItems({status, siteId})`, `approveReviewItem(id, by)`, `reviseReviewItem(id, instruction, by)` in `review.ts`; HTTP for the super admin: `GET /api/builder/onboarding/review?status=pending&site=`, `POST {id, action: "approve"} | {id, action: "change", text}`. Item: id, onboardingId, siteId, siteKey, business, test, pageId, pageTitle, locale, sectionId, label, status, version, updatedAt, preview (plain text ≤ 600 chars), placeholders, lastComment, reviewUrl.
- **AI and cost:** every call goes through `aiComplete` (`recordAi` in `store.ts`), logged per record (purpose, model, tokens, cost; shown under "For the team"); per-record caps 120 calls / $0.50 on top of the monthly budget; a JSON answer that cannot be read is asked for once more; test records answer with canned text (`useMock`, set only by the super admin at creation, never from request input). **Voice:** the browser records, converts to 16 kHz mono WAV (`components/onboarding/voice-button.tsx`) and posts it to `/api/onboarding/[id]/voice` (max 4 MB ≈ 2 min) → `aiTranscribe` in `ai.ts` (OpenRouter `input_audio`, default `google/gemini-2.5-flash-lite`, audio $0.30 per million tokens; `CMS_AI_AUDIO_MODEL` overrides) → the transcript lands in the text box for checking. Measured (2026-11-19, real run "Onboarding TEST Cafe real", 2 pages LV + EN, 1 block rewrite): follow-ups $0.00004, brief $0.00033, two pages $0.00183, one rewrite $0.00016, translation of two pages $0.00146 → **about $0.004 per website** (gemini-2.5-flash-lite).

## Public page performance (2026-11-19)

- **Server-rendered website markup.** Public pages render the website on the server (`site-canvas-markup.tsx`: `SiteCanvasMarkup`, `canvasRootProps`, `checkoutTarget`) and ship only `site-runtime.tsx` to the browser (`SiteRuntime` + `useSiteRuntime`: menu, sliders, accordions, tabs, showcase, forms, shop/map/cart/account/booking widgets, lightbox). The template catalogue (`catalog.json`, ~1 MB) and the project document are no longer sent to visitors. The editor's `SiteCanvas` renders the same markup in the browser and uses the same hook, so both stay identical; add new public behaviours to `useSiteRuntime`, never to the markup module.
- **Responsive images.** `/api/builder/media/{site}/{id}?w=320|480|640|828|1080|1440|1920|2560` returns a resized WebP copy (q72), cached in `media/w/` next to the original (Blob installations: generated from the Blob upload, cached by the CDN; `Cache-Control: immutable`). `SectionRenderer` adds `srcset` (+ `sizes="100vw"` above the fold, `sizes="auto, 100vw"` for lazy images) to uploaded images whose template sets width and height; the height attribute is corrected to the picture's own ratio, so the box is the same as without a srcset. Blocks whose scripts swap picture sources (pricing-v22 product thumbnails, pricing-v23 configurator, services-v4 accordion) keep plain `src`. Helper: `lib/builder/responsive-image.ts`.
- **Library pictures** (`public/images/**`): `scripts/image-variants.mjs` (run by `import:sections`, or `npm run images:variants`) writes WebP copies to `public/images/_w/` and `lib/builder/static-images.json`; `responsiveImage()` gives them the same srcset treatment as uploads.
- **Library CSS per page.** `scripts/build-site-css.mjs` (prebuild, `import:sections`, `npm run site-css`) compiles `site.scss` in parts — base (foundation + index), each family in its @use order, refresh, the website shell ("site") — into `lib/builder/site-css.json` (order + content hashes) and `lib/builder/site-css-content.json` (the CSS). A public page links ONE stylesheet, `/api/site-css/base+header+footer+…+refresh+site.<hash>.css` (`lib/builder/site-css.ts` → `app/api/site-css/[bundle]/route.ts`): base, header, footer, the families of its sections, refresh and site concatenated in that order, immutable cache (the hash changes with the CSS). Also included: a family whose classes a template borrows, `content` for rich text, `calculator` for pop-up sections, `contact` for #account/#search/#chat links. The route accepts only known parts in site.scss order. In development the bundle is compiled live from the SCSS, so edits show without a rebuild. The editor canvas and the library pages still import the whole `site.scss`. Keep family SCSS self-contained (no rules for other families' blocks); a new family = a new `@use` line in `site.scss`, picked up automatically.
- **Above the fold.** Images of the page's first section (and of the H1 section) load eagerly; the first of them gets `fetchpriority="high"`, all others `decoding="async"` + lazy. Background video (hero-v52) has no `autoplay` and `preload="none"` in the markup; `site-widgets.ts` starts it after the `load` event, so the poster stays the LCP element.
- **Fonts.** Public pages use self-hosted copies of the website fonts: `public/fonts/*.woff2` + `public/fonts/site-fonts.<hash>.css` (a static file linked by `app/site/layout.tsx`, so its url()s match the preloads) (the same Google Fonts files, @font-face rules and size-adjusted fallbacks next/font produced for `components/builder/site-fonts.ts` and the Inter/Playfair root fonts; generated by `scripts/extract-site-fonts.mjs .next/static` from a production build — regenerate after adding a font or pair). `public-page.tsx` can preload only the website's own pair — switched OFF (`PRELOAD_SITE_FONTS` in `lib/builder/font-preload.ts`): in the A/B of 2026-11-19 it made LCP worse on every page — (`lib/builder/font-preload.ts`: heading face in the pair's heading weight + body face in 400, only the subsets of the page language: lv = latin + latin-ext, ru = latin + cyrillic, else latin; file list in `lib/builder/site-font-files.json`). The editor canvas and the admin keep next/font. `/fonts/*` is served with an immutable cache.
- **Two root layouts.** Admin routes (login, dashboard, editor canvas, library, order, onboarding, booking/cancel, `/`) live in the route group `app/(admin)/` with `app/(admin)/layout.tsx` (Tailwind/shadcn `globals.css`, admin fonts); `TooltipProvider` (base-ui) is in `app/(admin)/dashboard/layout.tsx`. Public website pages have their own root layout `app/site/layout.tsx` with `app/site/site-base.css` (only Tailwind preflight, the former base rules, `:root` tokens, the html/body classes and Tailwind's `.container` utility — the one utility class templates use) + `site.scss`: no admin utilities/shadcn CSS (−18 KB gzip render-blocking CSS). Moving between a website and the admin is a full page load. API routes, `robots.ts` and icons stay at the app root. Keep templates free of Tailwind utility classes (they are not in the public CSS); when a public page needs a new base rule, add it to `site-base.css`. The form token is fetched only on pages that have a form.
- **Accessibility guards.** Websites with a style preset: muted text is darkened/lightened until it reaches 4.5:1 on the background and cards (`readableMuted` in `style-presets.ts`), and on accent-toned sections (`site.scss`). Menu items without a page or address render as `<span>` (no href-less links). Pixel-matched clones (no preset) keep their original colours.

Results: `before/`, `after/`, `summary.md`. On local/tunnel hosts every page is `noindex` by design, so the Lighthouse SEO score there is capped (is-crawlable); on the website's own domain that audit passes.
