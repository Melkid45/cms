# Harbstone builder

The admin now uses only the approved library at `frontend/src/components/{sections,layout}`. `scripts/import-sections.mjs` compiles those templates into a typed React node registry with editable field bindings and copies shared images. Pages store variation IDs and content values, never arbitrary HTML. Shared SCSS is imported directly from the frontend; typography stays in its common files. To refresh after changing a source template, run `npm run import:sections`, review field mapping if the structure changed, and refresh the matching screenshots. IDs are unique per section instance.

The page renderer uses the common `section-stack` rhythm (200px at 1920px, 150px at 1440px, 64px minimum). The shared container explicitly resets Tailwind's breakpoint max-width; it is 1820px wide at 1920px and fluid on smaller screens. Header and footer menus have separate placements and editing panels. Older projects that shared a group receive an independent footer copy without losing their existing links; subsequent saves persist the separation. The server rejects cross-placement assignments.

## Local use

Run `npm run dev -- --hostname 127.0.0.1`. Open `/dashboard/pages`. The Northline Studio sample has Home, Studio and Services at `/site/home`, `/site/studio`, `/site/services`. **Save draft never changes the published page. Publish page updates its public snapshot.** Public routes receive only published snapshots, without draft content or history. Draft slugs and current published URLs are reserved until publication. Layout, menus, brand and form settings are shared site settings and take effect when saved.

Text, images, SEO, section ordering, duplication, layout, multiple menu groups, two-level menus, colors and header/footer logos are connected. Sections can be dragged by their handle, moved with arrow buttons, or hidden without deleting content. Repeated-card variations expose Add, Remove, Duplicate and Move controls (1–30 items per group); fixed compositions and linked-tab layouts keep their original structure. Shared fields are grouped into introduction, images and links. Variation changes map content by semantic role, including custom card lists between repeatable variations. Switching a custom list to a fixed composition requires confirmation.

Page history keeps the last 20 previous versions. Restore loads a snapshot into the editor; save or publish deliberately afterwards. Deletion moves a page to Trash and hides its public URL and navigation links. Restore retains the published snapshot and its menu references. A conflicting slug must be resolved before restoring. Change the homepage before moving it to Trash. Keep external backups in addition to this short revision history.

Locally, content and uploaded images are stored in ignored `.data/`, on the server instead of localStorage/IndexedDB. They survive browser and server restarts. Back up that directory with the project. Concurrent edits are protected by revision checks: stale saves return HTTP 409 instead of overwriting newer content. Images are validated/decoded, resized, stripped of metadata and stored as WebP. Plain SVG logos are parsed with a strict element allowlist, reject scripts and external resources, and are rasterized before storage. Original source files and all previous static frontend demo pages are preserved. Old builder renderers/catalog/local browser storage adapters were removed from the admin.

## Vercel / persistent hosting

Configure **DATABASE_URL** for PostgreSQL, **BLOB_READ_WRITE_TOKEN** for Vercel Blob, **CMS_ADMIN_EMAIL**, a unique **CMS_ADMIN_PASSWORD** of at least 12 characters, **CMS_AUTH_SECRET** of at least 32 random characters, and **NEXT_PUBLIC_SITE_URL** for the public domain used in sharing metadata. Use `hosting.env.example` as the checklist and run `npm run check:deploy`. This checks configuration presence; it does not prove external connectivity. Do not commit secrets. The adapter creates its table on first connection. A serverless filesystem is not treated as persistent: hosted writes fail explicitly without storage configuration.

Sign in at `/login` with the configured owner email and password. Dashboard routes and APIs require a signed HttpOnly, SameSite=Strict session with a server-verified 12-hour expiry (Secure in production). Logout clears it. Login attempts are rate-limited in persistent storage. Changing the owner email/password/secret requires server environment access; rotate the authentication secret to revoke all sessions. Open registration redirects to login. Team accounts and automated password recovery are not implemented. Unconfigured local development remains accessible without credentials; production fails closed.

## Enquiries & SMTP

Published contact/footer forms submit to `/api/forms`. Messages are saved in `/dashboard/submissions` before email delivery is attempted. Forms in library/editor previews never send messages. `/dashboard/settings/forms` controls acceptance, recipient and success message, and shows which hosting integrations are configured. Anti-spam uses a hidden field, a signed token valid for 30 minutes (minimum age one second), and a durable per-IP limit of five submissions per ten minutes. Only fields from the actual published form are accepted and validated. IPs are hashed with the server secret. Expired rate-limit entries are cleaned automatically.

Set **SMTP_HOST**, **SMTP_PORT** (587 by default), **SMTP_SECURE** (`true` for port 465), **SMTP_FROM**, and, when required, **SMTP_USER** / **SMTP_PASSWORD** in the server environment. SMTP credentials are never stored in the project JSON or returned to the browser. Inbox distinguishes saved, emailed and failed delivery; failed mail does not lose the enquiry. Actual mail delivery must be tested with the client's provider before launch. Up to 5,000 messages are retained; at capacity new enquiries fail explicitly instead of silently deleting older data. No external email is sent while SMTP is unconfigured.

The existing `harbcms.vercel.app` deployment serves the static `frontend` project. The Next builder is a separate application rooted at `admin`; it needs its own Vercel project or a deliberate switch of deployment root. Publishing content in the Next builder is a database operation and needs no Git push/rebuild. Telegram code editing continues to publish the static frontend separately. Do not imply these are the same deployment.

## Verification

`npm run test:blocks`, `npm run lint`, `npx tsc --noEmit`, `npm run build`. Against the local development server: `npm run test:api`, `npm run test:workflows`. The latter creates/removes its own test page and leaves a clearly marked demo enquiry in Inbox; run only against a test environment with SMTP disabled.

105 real desktop screenshots are in `public/previews`. The library has 94 content variations, six headers and five footers. Images in the picker come from the media library; changing a field never changes another block's content. Header/footer menu links reference stable page IDs, so renaming a page's slug updates navigation automatically. A page cannot be removed while selected as the homepage.
